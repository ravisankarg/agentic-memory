Benchmark field manual

Test the memory, the reader, and the agent separately.

No public score tells the whole story. This guide maps the major suites, their version traps, and a three-layer harness that produces actionable evidence.

The evaluation stack

One system, three different questions

IR

Did search find the evidence?

Evaluate gold source IDs before an answer model can hide the miss. Use strict all-evidence recall for multi-hop questions.

QA

Could a fixed reader use it?

Freeze the reader, prompt, temperature, and token budget. Compare retrieved context with oracle evidence and full context.

AG

Did memory improve action?

Run multi-session tasks where earlier feedback matters. Measure success, progress, latency, and unsafe behavior.

Never collapse these layers into one score.

A system can retrieve the right evidence and still answer incorrectly; it can answer a public benchmark from parametric knowledge without using memory; and perfect recall can still fail to improve an agent’s plan.

Metrics that diagnose

Report more than Recall@k

Strict Recall-all@k

Did the result set contain every required evidence unit? Essential for multi-hop questions. Also report the unit: turn, session, fact, file, or trajectory.

Recall-any@k

Did at least one relevant item appear? Useful but optimistic when an answer requires several facts.

nDCG / MRR / precision

How early did good evidence appear, and how much irrelevant context competed with it?

Evidence quality

Wrong-user rate, stale-evidence rate, redundancy, source diversity, future leakage, and malicious-memory admission.

Fixed-reader outcomes

Correctness, temporal/update accuracy, abstention, citation support, groundedness, and oracle gap.

Systems curve

p50/p95 read latency, write/index latency, tokens, storage, update cost, and quality at a fixed token budget.

Compare at fixed token budget as well as fixed k.

Top-10 sessions and top-10 atomic facts can differ by orders of magnitude in context size. A fixed k comparison may reward systems that return much more text.

Three-layer harness

A benchmark design you can trust

Layer A · Fast component tests on every change

  1. Create a private sequential corpus with stable memory IDs and source spans. Split by user/conversation—not by question.
  2. Cover exact entities, paraphrases, all-evidence multi-hop, “as of” time, corrections, scope, procedural lessons, duplicates, conflicts, and unanswerable cases.
  3. Feed the same chunks to BM25, dense, hybrid, reranked hybrid, and agentic retrieval wherever possible.
  4. Cache retrieved IDs and scores so regressions can be diffed without an answer model.

Layer B · Fixed-reader end-to-end QA

  1. Use one pinned reader/model, prompt, temperature, and context budget.
  2. Score structured answers directly. Use an LLM judge only for legitimate open-ended paraphrase, and pin its exact version and rubric.
  3. Include no-memory, full-context, and oracle-evidence controls.
  4. Log whether each error was a retrieval miss, stale/conflicting evidence, reader failure, or abstention failure.

Layer C · Scheduled whole-agent tasks

  1. Ingest events sequentially; do not bulk-index the final state only.
  2. Allow earlier task feedback to alter later tasks.
  3. Measure task success and progress alongside memory reads/writes, latency, token spend, and safety failures.
  4. Group statistical tests by independent user/conversation/task group, not question, because many questions share a history.

Reproducibility

Pin everything that can change the answer

Data

Dataset commit and hash, subset, split unit, timestamp policy, hidden canaries, random seed.

Writer

Extraction prompt/model, chunk schedule, update/overwrite policy, consolidation frequency.

Index

Chunker, contextualization, embedder, vector dimensions, ANN settings, BM25 tokenizer, graph builder.

Query

Filters, rewrites, candidate k, fusion constant, reranker, MMR, expansion, evidence token budget.

Reader

Model snapshot, system/user prompt, temperature, max output, evidence format, citation policy.

Judge

Exact rubric, model snapshot, rationale, retries, parsing, human agreement sample.

Hide benchmark plumbing from the memory system.

Do not expose question type, benchmark name, gold answer, evidence IDs, future timestamps, or file paths that encode relevance. LongMemEval-V2’s anti-leak design is a useful model.

Four-week launch plan

From zero to credible benchmark

WEEK 1

Private gold set

Author 100 product-shaped queries over 10 independent histories. Include scope, update, temporal, multi-hop, procedural, malicious, and unanswerable cases.

WEEK 2

Retrieval baselines

Implement BM25, dense, hybrid RRF, and hybrid + reranker. Freeze ingestion and report strict recall plus latency at fixed token budgets.

WEEK 3

Public replication

Run cleaned LongMemEval and current LoCoMo with frozen reader, oracle, no-memory, and full-context controls.

WEEK 4

Target the failure mode

Add temporal resolution, hierarchy, graph, or agentic file search only where per-capability error analysis shows a clear gap.
