01 · Mental model

What is agentic memory?

Agentic memory is persistent state that an agent can write, update, search, and use in later decisions. It lives outside the model’s fixed weights and outside the current prompt, but it can be brought into working context when needed.

Memory is not one thing.

A complete system has a canonical store, memory representations, derived indexes, a retrieval policy, a reader, and an update/forgetting lifecycle. Calling a vector database “the memory” hides most of the hard problems.

WM

Working memory

The current goal, recent messages, plan, and selected evidence. Fast and directly visible to the model, but bounded and ephemeral.

EP

Episodic memory

What happened: situations, actions, observations, outcomes, timestamps, and lessons from particular attempts.

SM

Semantic memory

What is believed to be true: user preferences, entity facts, project decisions, relationships, and current state.

PM

Procedural memory

How to act: policies, prompts, skills, runbooks, successful workflows, failure modes, and stop rules.

This working/episodic/semantic/procedural split is a useful research taxonomy, described explicitly by CoALA and adopted in framework guidance such as LangGraph’s memory overview. It is not a mandatory storage format. One Markdown file can mix all four types—but doing so makes search, updates, trust, and deletion harder.

Four layers that people often confuse

1Canonical evidenceRaw messages, tool results, files, events, and trajectories.
2Derived memoryAtomic facts, episodes, summaries, profiles, and procedures.
3Search indexesFTS/BM25, vectors, entity graph, time and metadata indexes.
4Evidence packA small, cited context assembled for this question and reader.

The safe rule is: raw evidence is canonical; summaries and indexes are rebuildable views. A lossy summary should never become the only surviving copy of what happened.

02 · File conventions

What are USER.md, MEMORY.md, and daily files?

They are recognizable conventions in file-based agents, but the names and loading behavior differ by product. The architecture matters more than the exact filenames.

ArtifactGood meaningLoading policyCommon failure
USER.mdSmall, current user preferences and interaction directivesAlways on or high-priority lookupBecomes a speculative dossier or stores secrets
MEMORY.mdCurated durable facts, decisions, and pointers to deeper memorySmall bootstrap/indexTurns into a monolithic transcript dump
memory/YYYY-MM-DD.mdAppend-mostly daily observations and session summariesRetrieved on demand; perhaps today/yesterday at startupTemporary guesses promoted as timeless truth
entities/*.mdFacts and changes centered on a person, project, place, or systemEntity-aware retrievalDuplicate aliases and unresolved contradictions
procedures/*.mdReviewed skills, workflows, policies, and gotchasTask/trigger routingUntrusted text silently changes agent behavior
events/*.jsonlMachine-readable append-only event log with source IDsNever inject wholesaleTreated as prompt-ready prose
Use ISO dates, not memory.ddmmyy.md.

2026-09-22.md is unambiguous, sorts chronologically as text, supports range scans, and composes cleanly with timestamps such as 2026-09-22T16-40-00Z--release.md.

What actual systems do

  • OpenClaw explicitly documents USER.md, a curated MEMORY.md, and memory/YYYY-MM-DD.md working notes.
  • Letta MemFS keeps always-loaded Markdown under system/; other memory files remain out of context until an agent searches or reads them.
  • Claude Code uses layered CLAUDE.md files primarily for project/user instructions—not a universal fact-memory schema.
  • AGENTS.md is an open, free-form repository instruction convention. It is useful procedural context, not a standardized long-term memory interchange format.
  • Database-oriented systems usually store typed JSON records under user/project namespaces rather than prescribing filenames.

The convergent pattern: progressive disclosure

Always visible

Small bootstrap layer

  • Critical constraints and identity
  • A few current user preferences
  • High-signal project decisions
  • Pointers into deeper topics
On demand

Deep memory layer

  • Topic, entity, and episode files
  • Detailed daily notes and trajectories
  • Raw sources and provenance
  • Rebuildable lexical/vector indexes

A short index gives the model orientation; precise search retrieves detail. This avoids paying the token and attention cost of every memory on every turn.

03 · Recommended structure

A transparent, local-first memory layout

This is a recommended synthesis—not a standard. It keeps human-readable canonical files while leaving room for a database-backed production implementation.

agentic-memory/
├── AGENTS.md                    # operator-authored behavior, not learned facts
├── memory/
│   ├── USER.md                  # tiny, current, user-reviewable directives
│   ├── MEMORY.md                # curated index and durable decisions
│   ├── daily/
│   │   └── 2026-09-22.md        # append-mostly working evidence
│   ├── entities/
│   │   └── project-agentic-memory.md
│   ├── episodes/                # situation → action → outcome → lesson
│   ├── procedures/              # reviewed runbooks and skills
│   ├── sources/                 # raw session/tool/file evidence
│   └── tombstones/              # deletions and re-ingestion guards
└── .memory-index/               # disposable FTS/vector/graph artifacts

For small, single-user systems, Markdown plus SQLite FTS5 is enough to start. For multi-user production, keep Markdown as an export/projection while Postgres or SQLite holds atomic records, access controls, valid-time fields, transactions, and deletion lineage.

One coherent claim per record

---
id: mem_01K5Q9W8D2
type: preference              # fact | episode | reflection | procedure
scope:
  tenant_id: personal
  user_id: user_001
  project_id: agentic-memory
status: active               # superseded | disputed | expired | retracted
observed_at: 2026-09-22T10:30:00+05:30
valid_from: 2026-09-22
valid_until:
source_refs:
  - session_id: s_456
    turn_id: t_18
provenance: explicit_user    # verified_tool | observed | inferred | derived
trust: trusted               # untrusted | reviewed
confidence: high
sensitivity: personal        # public | internal | secret
entities: [user:user_001]
supersedes: []
retention: until_superseded
---

Prefer concise progress updates while implementation is running.

Why each field exists

Scope

Authorization and tenancy are hard filters. Similarity must never decide which user’s memories are visible.

Two kinds of time

observed_at records when the system learned something; valid_from/to records when it was true.

Provenance

Explicit user statements, tool-verified facts, observations, and inferences deserve different trust and promotion rules.

Supersession

Append and link changes instead of silently overwriting history. Retrieval can resolve the current view.

The write lifecycle

CAPTURE

Keep source identity

Actor, role, session, time, tool, artifact, and exact source span.

ADMIT

Apply trust and privacy policy

Reject secrets, unnecessary personal data, unsupported claims, and untrusted behavior-changing instructions.

EXTRACT

Create atomic memories

Classify facts, preferences, episodes, reflections, and procedures. Keep source links.

CONSOLIDATE

Add, merge, supersede, or skip

Run heavier summarization asynchronously; never blindly append every sentence as a permanent memory.

INDEX

Build disposable search views

Lexical, vector, temporal, entity, and hierarchy indexes derive from canonical records.

REVIEW

Promote, decay, archive, delete

Decay retrieval priority where appropriate; propagate deletion through summaries, vectors, caches, and backups.

04 · Context economics

Why retrieve? Why not load every file?

A context window is working memory, not a durable archive. Retrieval is the controlled read operation that moves the right long-term memories into that window.

01

Capacity

Histories grow without bound; a context window does not. Every turn, tool trace, screenshot, and revision compounds.

02

Attention

Evidence can be “lost in the middle.” Irrelevant and stale memories compete with what matters now.

03

Cost

Repeatedly reading millions of tokens increases latency and inference cost—even if a model technically accepts them.

04

Freshness

Current facts, historical facts, and contradictions need explicit temporal resolution, not a flat pile of prose.

05

Security

Least-privilege filtering must happen before ranking. A full dump can cross user, project, or sensitivity boundaries.

06

Diagnosis

A retrieval trace lets you distinguish “evidence not found” from “evidence found but read incorrectly.”

Lost in the Middle showed that long-context models can use evidence unevenly depending on its position. LongMemEval later found 30–60% QA degradation on ~115K-token histories relative to oracle evidence for the tested models. Longer context has improved since, but the architectural lesson remains: advertised capacity is not guaranteed usable memory.

When loading everything is the right answer

Retrieval introduces its own failure mode: a necessary memory can be missed. Full context can be better when the corpus is small, the task requires holistic synthesis, prompt caching makes repeated reads cheap, or retrieval confidence is low. Anthropic’s Contextual Retrieval guide suggests full prompting can be simplest for a knowledge base under roughly 200K tokens in its tested setting. Treat that as a model- and workload-specific heuristic, not a law.

A controlled RAG-versus-long-context study similarly found that sufficiently resourced long context often won on average quality while RAG retained a large cost advantage. The practical design is a router: retrieve by default as memory grows, but keep full-context or broader file inspection as a fallback and evaluation baseline.

05 · Retrieval engineering

The production retrieval stack

The strongest practical default is not “pick an embedding model.” It is a staged pipeline in which cheap signals maximize recall and expensive reasoning improves precision.

1UnderstandPreserve exact strings; detect entities, time, scope, query type, and memory type.
2ConstrainApply authorization, project, status, sensitivity, and valid-time filters first.
3RecallRun BM25/FTS and dense or late-interaction retrieval in parallel.
4FuseCombine incomparable rankings with reciprocal rank fusion.
5RerankJointly score query + candidate with a cross-encoder or strong reranker.
6DiversifyRemove duplicates; use MMR or coverage constraints to protect context budget.
7ExpandAdd headers, adjacent turns, timestamps, parent episode, and source spans.
8IterateFor missing/multi-hop evidence, search again; otherwise abstain with provenance.

Why simple dense embedding search is not enough

Dense-only

One query, one vector, top-k

  • Fast semantic shortlist
  • Easy to implement and scale
  • Compresses every memory into one point
  • No inherent current-state or permission logic
  • No guarantee all multi-hop evidence appears
Composite retrieval

Constrain, ensemble, reason, cite

  • Exact and semantic signals complement each other
  • Time and scope are explicit filters
  • Reranking sees query and evidence together
  • Graph/hierarchy adds structure when justified
  • An agent can search again if evidence is incomplete

BEIR found BM25 a robust zero-shot baseline and late interaction/reranking strong but more expensive. BRIGHT showed why general retrieval scores are insufficient: models strong on conventional leaderboards performed poorly when document relevance required reasoning, while reasoning-expanded queries improved nDCG@10 by as much as 12.2 points in its experiments.

06 · State of the field

What is “state of the art” in 2026?

There is no universal winner. Exact recall, temporal state, associative multi-hop, dialogue personalization, global synthesis, and procedural experience are different tasks. System scores also mix the writer, store, retriever, controller, reader, and judge.

Better wording than “the SOTA system”

“This method is on the accuracy/latency frontier for this benchmark, corpus version, reader, prompt, and token budget.”

The result most relevant to file-based memory

LongMemEval-V2 evaluates evidence gathering over web-agent trajectories containing up to 115 million tokens. Its paper reports:

AgentRunbook-C stores full trajectories as files, generates concise and full manifests, provides trajectory-inspection helpers, and asks a coding agent to select bounded supporting spans. It outperformed the paper’s fixed RAG baselines because the controller can adapt its search path to the question. It was also much slower. This is not proof that “grep beats vectors”; it is evidence that adaptive evidence gathering can beat a one-shot similarity pipeline when memory contains workflows, state transitions, images, and local gotchas.

The durable frontier pattern

Constrained hybrid retrieval + strong reranking + temporal/graph/hierarchical organization + adaptive multi-step search when justified. Start simple, measure failure types, and add structure only when an ablation proves it closes real misses.

07 · Jump-start plan

Build the first benchmarkable system

The goal is not an impressive demo score. It is a reproducible experiment that tells you which layer fails and why.

Starter architecture

  1. Canonical Markdown + JSONL. Human-readable memory files with stable IDs and source spans; append-only raw events.
  2. SQLite sidecar. Metadata tables plus FTS5/BM25. Rebuild it from canonical files.
  3. Dense vectors. Use exact flat search while small. Introduce HNSW only after scale tests show it is needed.
  4. Hybrid candidate generation. Fetch broad lexical and dense pools in parallel, then fuse with RRF.
  5. Rerank and budget. Cross-encode the shortlist, deduplicate, diversify, and expand source context within a fixed token budget.
  6. Escalation path. If evidence is incomplete: query rewrite, temporal/entity expansion, agentic file scan, full-context read, or abstention.

Measure three layers separately

Component

Retrieval

Strict Recall-all@k, Recall-any@k, nDCG@k, MRR, precision, stale/wrong-user evidence, redundancy, and context tokens.

Fixed reader

Memory QA

Answer accuracy, temporal/update correctness, abstention, citation support, and groundedness with one frozen reader.

Whole agent

Task outcome

Success, progress, safety violations, p50/p95 latency, read/write cost, and behavior across multiple sessions.

Always include oracle evidence, no memory, and full context when feasible. The oracle gap measures reader/reasoning failure; the gap from oracle to retrieved evidence measures memory/retrieval failure.

08 · Trust boundary

Memory is an attack surface

A poisoned memory can influence later sessions after the original malicious input is gone. Retrieved content must be evidence—not an automatic extension of the system prompt.

Scope before search

Enforce tenant, user, agent, project, sensitivity, and authorization as database predicates before candidate generation.

Separate facts from directives

A remembered sentence about a procedure must not gain tool authority merely because it is similar to the current task.

Provenance-gated promotion

Untrusted web, email, document, or tool output cannot directly promote itself into core or procedural memory.

Lineage-aware deletion

Delete the canonical record and every derived summary, embedding, cache, graph edge, and retrievable backup copy covered by policy.

Version changing truth

Keep historical events; mark current facts with validity and supersession. Do not resolve conflicts by recency alone.

Fail closed

If no evidence clears a calibrated threshold, broaden search safely or abstain. Never turn low cosine similarity into confident memory.

Tests most teams forget

  • Wrong-user and wrong-project memory that is semantically perfect for the query.
  • A newer correction that contradicts a highly similar older statement.
  • A future-dated fact accidentally visible to an “as of last month” query.
  • Malicious instructions embedded in a retrieved web page or tool output.
  • Five near-duplicate memories crowding out one complementary evidence item.
  • A deletion that survives in a summary, vector index, cache, or entity graph.
  • An unanswerable question that tempts the model to force-fit a nearby memory.

OWASP’s 2026 memory attack-surface guidance treats persistent context corruption as a distinct agent risk. Design the admission and retrieval gates as security controls, not prompt suggestions.

09 · Keep this

The shortest useful summary

A good memory system is a cited, versioned, access-controlled evidence service for an agent.

Files are a transparent canonical interface. Retrieval is query-time attention allocation. Dense vectors are one signal. Benchmarks must separate retrieval from reading and reading from action.

  1. Keep USER.md tiny, explicit, current, and user-reviewable.
  2. Use MEMORY.md as a curated router—not a warehouse.
  3. Use ISO-dated append-mostly notes for episodes and evidence.
  4. Store provenance, scope, valid time, and supersession with every durable memory.
  5. Start with BM25 + dense + RRF + reranking; add graph/hierarchy/agents only for measured misses.
  6. Keep full-context and direct file search as fallbacks and evaluation controls.
  7. Pin every benchmark component and report an accuracy–latency–cost frontier, not one magic score.
